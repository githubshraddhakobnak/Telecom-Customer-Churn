# Telecom Customer Churn Analysis

A reproducible portfolio project for a data analyst moving into a new role. It covers data quality, SQL analysis, customer segmentation, visualization, and a logistic regression baseline.

**Data is synthetic, not real customer data. All findings are demonstrations, not measured business impact.** The generator intentionally creates relationships between contract, tenure, complaints, and churn. Model performance on this data does not establish real-world predictive ability.

## Run locally

Requires Python 3.8 or newer. No third-party packages, credentials, or downloads are needed.

```bash
python -m src.generate_data
python -m src.analyze
python -m src.model
python -m unittest discover -s tests -v
```

Run commands from the repository root. The repository includes the generated data and reports, so you can also inspect the results immediately. Open `reports/summary.md`, the SVG charts, and `reports/model_metrics.json`.

## Business questions

1. Which contracts and tenure groups have the highest observed churn?
2. How are complaints and service usage associated with churn?
3. Can information available before a future churn window help prioritize outreach?
4. How much monthly recurring revenue is represented by customers who subsequently churn?

## Analytical approach

The data represents one row per customer active at a fictional snapshot date. Features describe history available at that snapshot. `churn` describes departure in the following 30 days. This framing avoids using post-departure information as predictors.

SQL calculates churn rate, segment population, and revenue exposure. The Python analysis uses the same SQL files in a local SQLite database. A fixed, stratified 60/20/20 train/validation/test split supports a small logistic regression baseline. Numeric scaling is fitted only on training rows; categorical levels are predefined. Validation F1 selects a threshold from a fixed grid. The held-out test set is evaluated once after selection.

The model uses a transparent standard-library implementation to make the mechanics inspectable. It is an educational baseline, not a production scoring service. See `docs/methodology.md` for assumptions and limits.

## How to interpret results

- Churn rate = churned customers / all customers in the group.
- Monthly revenue exposure sums snapshot monthly charges for customers who subsequently churn. It is neither realized revenue loss nor customer lifetime value.
- Observational differences are associations. A randomized retention experiment is needed to estimate intervention impact.
- A probability threshold is not a campaign recommendation. Capacity, offer cost, expected incremental retention, and margin must inform outreach decisions.

## Adapt to a real dataset

Map an authorized, de-identified dataset to the schema in `data/DATA_DICTIONARY.md`, preserving a clear snapshot and outcome window. Do not commit customer identifiers or raw private data. Replace the random split with time-based evaluation, establish a leakage review, and validate calibration and subgroup performance before operational use.
